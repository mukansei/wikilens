# 설계 제안: 임베딩 기반 학습 표현

**상태: 제안. 아직 결정 안 됨.** 구현 전 검토용. 결정이 나면 `DECISIONS.md`로
옮기고(채택/기각 어느 쪽이든) 이 파일은 지운다.

## 문제

`TrajectoryStore`는 학습 신호를 **항(term) 문자열 단위**로 누적한다
(`postings: term -> pageId -> (hits, misses)`, `server/src/main/kotlin/dev/wikilens/learn/TrajectoryStore.kt`).
Coway 실데이터로 오늘 실측한 두 갭이 전부 이 표현 방식에서 나온다:

1. **진짜 동의어 무력화** — "행사 정책 문서 어디서 볼 수 있어?"는 "이벤트
   정책서"로 3번 학습시켜도 전혀 도움을 못 받는다. `learnedHints: 0`으로
   실측 확인됨. "행사"와 "이벤트"는 문자열이 다른 항이라 애초에 연결될 방법이
   없다.
2. **커버리지 희석** — `hints()`가 `ebLower(...) × (질의 토큰 중 학습된 것의
   비율)`로 신뢰도를 깎는다(`TrajectoryStore.kt:190`). "상조" 자체는 3번 다
   학습됐어도, 질의에 "관련해서 참고할"처럼 부가어가 많이 붙으면 커버리지
   비율이 낮아져 임계값(0.45) 밑으로 떨어진다. 실측: "상조 관련 문서 어디
   있어?"(4토큰)는 학습 후 성공, "상조 관련해서 참고할 문서 어디 있어?"
   (6토큰)는 같은 학습으로도 실패.

두 갭 다 **검색 랭킹(BM25/Lucene)의 문제가 아니다** — 검증됨: 같은 갭이 BM25를
안 거치고 `TrajectoryStore.hints()` 직접 호출 결과에서도 그대로 나타난다.
학습 레이어의 표현 자체가 어휘 완전 일치를 전제한다는 게 원인이다.

## 왜 지금 이 문제가 중요한가

서버를 두는 이유를 오늘 대화에서 다시 정의했다: **한 번의 검색을 더 잘하는 게
아니라, 세션을 넘어 누적되는 학습**이다. Claude Code가 `ALIASES.md`를 그
자리에서 잘 읽는 것과 서버가 갖는 값어치는 별개 질문이고, 후자는 정확히
"여러 사람이 다르게 표현해도 다음 사람에게 도움이 되는가"에 있다. 지금
표현(항 단위)은 정확히 같은 표현이 반복돼야만 이 값어치가 나온다 — 오늘
실측한 두 갭이 그 한계의 직접적 증거다.

## 제안: 학습 표현을 벡터 유사도 기반으로

### 유지할 것

- **Gate 분류** (`Scoring.kt`의 `Gate.classify`) — TRACING/RATIONALE 질의를
  걸러내는 로직은 "이 질의를 학습해도 되는가"의 문제고, 표현 방식과 무관하다.
  그대로 둔다.
- **Empirical Bayes 하한 계산** (`Reliability.ebLower`) — hits/misses로부터
  신뢰도 하한을 구하는 통계 자체는 바뀔 이유가 없다. **무엇을 하나의
  관측으로 셀지**만 바뀐다.
- **이중 확정 방지, 재구성 신호, append-only 영속화** — 전부 "관측을 어떻게
  기록하는가"의 문제라 표현 방식과 독립적이다.

### 바뀌는 것

```
지금:  postings[term][pageId] = (hits, misses)
제안:  observations[pageId] = [(queryEmbedding, success), ...]  (또는 누적 centroid)
```

질의 시점에 새 질의를 임베딩하고, 각 후보 페이지의 과거 관측 임베딩들과
코사인 유사도를 구해 **유사도로 가중한 hits/misses**를 `ebLower`에 넣는다.
문자열이 아니라 의미로 근접하면 근접한 만큼 신뢰도가 옮겨간다.

### `learn/`의 순수성 계약을 지키는 배치

CLAUDE.md의 절대 계약: **"`learn/`에 Spring·Lucene import가 없다 —
`check-contracts.sh`가 강제한다."** 임베딩 계산 자체(모델 로딩, 추론)는 이 제약을
깨기 쉽다. 그래서 경계를 명확히 나눈다:

- `learn/` 패키지는 **`FloatArray`(임베딩 벡터)만 입력으로 받는다.** 코사인
  유사도 계산은 순수 수학이라 의존성이 없다 — 계약이 그대로 유지됨
  가능하다.
- 임베딩을 **계산**하는 코드(모델 호출)는 `learn/` 밖의 새 패키지
  (예: `embed/`)에 둔다. `Controller`가 질의 문자열을 받으면 `embed/`를 거쳐
  벡터로 바꾼 뒤 `learn/`에 넘긴다.

## 열린 질문 (구현 전에 결정 필요)

### 1. 임베딩을 어디서 계산하나

| 옵션 | 장점 | 단점 |
|---|---|---|
| 외부 API 호출 (질의마다) | 구현 간단 | 매 검색마다 네트워크 왕복 — `Gate.classify`가 "LLM 호출 없이 어휘 규칙으로만 판정"하는 이유(Minton의 효용 문제, 아끼려던 비용을 되불러들임)가 **똑같이 적용된다** |
| 로컬 임베딩 모델(JVM 내 ONNX 등) | 네트워크 의존 없음, 지연 낮음 | 배포 복잡도 증가, 모델 관리 필요 |

이 프로젝트가 지금까지 일관되게 "LLM/무거운 모델을 조회 경로에 넣지 않는다"는
원칙을 지켜왔다는 걸 감안하면, 로컬 모델 쪽이 철학에 더 맞는다. 다만 어떤
경우든 **지연 시간 실측이 선행돼야** 이 트레이드오프가 맞는지 판단할 수 있다
— 지금은 가정이다.

### 2. 한국어 다국어 임베딩 모델 선택

Coway 실데이터에 베트남어 페이지도 섞여 있는 걸 오늘 확인했다(`TREE.md`
생성 결과 참고). 한국어 전용이 아니라 다국어 지원 모델이 필요할 가능성이
높다. 후보 선정과 한국어 성능 검증이 필요하다.

### 3. 커버리지 희석과 동일한 문제가 벡터에도 있을 수 있다

문자열 표현을 벡터로 바꾼다고 "긴 질의가 짧은 질의보다 불리하다"는 문제
자체가 사라진다는 보장은 없다. 긴 질의의 임베딩은 여러 개념이 섞여 평균화되며
분산될 수 있다 — 이것도 실측 전에는 가정이다.

### 4. 유사도 오탐 위험

BM25에서 본 "흔한 단어가 신호를 희석시키는" 문제의 임베딩판으로, **의미상
막연히 비슷하지만 실제로는 다른 문서**가 높은 유사도로 잘못 학습될 위험이
있다. 오늘 발견한 문제를 없애면서 새 문제를 안 만드는지 확인이 필요하다.

### 5. 보호된 계약 문서 수정 필요

CLAUDE.md의 "절대 깨면 안 되는 계약" 표에 다음 행이 있다:

> `항 단위 포스팅 (키워드 **집합** 아님)` | `TrajectoryStore` | `표현이 다르면
> 카운트 분산`

이 원칙 자체를 벡터 기반으로 대체하는 것이므로, 채택 시 **이 표를 명시적으로
갱신**해야 한다 — 조용히 우회하면 안 된다. `check-contracts.sh`에 이 계약을
직접 검사하는 항목은 없지만(문서로만 존재), `server/src/test/kotlin/dev/wikilens/learn/LearnLayerTest.kt`의
"표현이 달라도 신뢰도 합산" 테스트 케이스는 이 변경에 맞춰 다시 설계해야 한다.

## 검증 계획 (채택 여부 판단용)

이 프로젝트의 원칙대로 — 코드부터 짜지 말고 먼저 작은 프로토타입으로
오늘과 같은 방식의 실측이 필요하다:

1. Coway 데이터에서 오늘 확인한 실패 사례("행사"↔"이벤트", 커버리지 희석
   사례)를 고정 벤치마크로 삼는다.
2. 후보 임베딩 모델 1~2개로 이 사례들이 실제로 고쳐지는지 확인한다.
3. 지연 시간·계산 비용을 실측한다(로컬/API 옵션 둘 다).
4. 오탐(의미상 비슷하지만 다른 문서로 잘못 학습) 사례가 새로 생기는지
   확인한다.
5. 전부 확인된 뒤에만 `TrajectoryStore` 구조 변경에 들어간다.
