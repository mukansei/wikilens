# 비용 모델을 잰다 — 실행 전 설계 (2026-08-28)

## 왜

손익분기 `p_hit(n−1) > p_wrong` 의 유도(D2)는 세 갈래 비용을 전제한다:

    적중        1 읽기
    잘못된 힌트  1 + n 읽기      ← 이 n 이 검증된 적 없다
    힌트 없음    n 읽기

**`1+n` 은 잰 적이 없다.** "오답을 하나 읽고, 그다음 후보 n 개를 다 읽는다" 는 뜻인데
`n` 은 기본 `limit=8` 이다. 모델이 실제로 그렇게 행동하는지는 아무도 안 봤다.

이것이 중요한 이유: `pWrong` 이 게이트가 아니라는 것이 확인되면서
(`pWrong < (n−1)/n = 0.875`, 거의 항상 통과 —
[1x-gate](design-2026-08-28-1x-gate.md)) **판정의 무게가 전부 이 가정으로 옮겨왔다.**
`1+n` 이 아니라 `1+2` 라면 손익분기 식 자체를 다시 써야 한다.

## 무엇을 재나

**오답을 받은 세션이 그 뒤에 문서를 몇 개 더 읽는가.**

`bench/agent.py` 가 이미 `extra.tools` 와 `extra.args` 에 도구 호출을 **순서대로**
남긴다. 세션마다 이렇게 센다:

    first_read_idx   첫 read 호출 위치
    reads_total      read 호출 총 수
    gold_read_idx    정답(gold)을 읽은 위치 — 없으면 못 찾은 것
    searches_after   첫 오답 read 뒤의 search 재호출 수

**`reads_total − 1` 이 곧 "오답 뒤 추가 읽기" 다**(첫 읽기가 오답인 세션에서).
그 분포가 `n=8` 근처인지, 훨씬 작은지를 본다.

## 절차

    1. ONAP 볼트 싱크 (Meetings + DW) → 벤치 서버 :8790 에 english 로 색인
    2. bench/agent.py --cases C --groups (5그룹 전량) --reps 3
       → cold 로만 돈다. 학습을 끄는 것이 아니라 **아직 안 쌓인 상태**를 쓴다
    3. 세션별로 위 넷을 뽑아 분포를 낸다
    4. 첫 읽기가 오답인 세션만 골라 `reads_total − 1` 의 중앙값·분포를 본다

**cold 만 돌리는 이유:** 재려는 것은 학습 효과가 아니라 **모델이 틀린 첫 후보를 받았을
때의 행동**이다. 학습 힌트가 있으면 그 행동이 바뀌므로 섞으면 안 된다.

**`--cases C` 만:** 서버판이라야 `search` 결과 순위와 `read` 대상이 도구 인자로 남는다.
A(원시 grep)·B(로컬판)는 `Bash`·`Grep` 이라 읽기 개수를 같은 기준으로 못 센다.

## 예측 (실행 전)

- **`1+n` 은 과대평가다.** 중앙값이 `1+8=9` 가 아니라 **3 이하**로 나올 것으로 본다.
  모델은 후보를 다 읽지 않고 제목만 보고 재질의하는 쪽이 싸다는 것을 안다.
- **재질의가 읽기를 대체한다.** `searches_after > 0` 인 세션이 절반을 넘을 것이다.
  그러면 비용은 읽기가 아니라 **턴**으로 나가고, 그건 D2 의 모델에 아예 없는 항이다.
- **그래서 문턱은 지금보다 느슨해진다** — 오답 비용이 작으면 `p_wrong` 을 더 허용한다.
  이미 0.875 인데 더 올라가면 `pWrong` 은 확실히 판정에서 뺀다.
- **딸림:** 못 찾고 끝난 세션(`gold_read_idx` 없음)이 섞인다. 그건 "오답 비용" 이
  아니라 "실패" 라 따로 센다.

## 판정

| 나온 값 | 하는 일 |
|---|---|
| 중앙값 ≈ `n` (8 근처) | D2 의 모델이 맞다. 손익분기 문턱을 그대로 둔다 |
| 중앙값 ≪ `n` (3 이하) | **모델을 다시 쓴다** — 오답 비용을 `1+k` 로 두고 `k` 를 실측값으로 |
| 재질의가 지배적 | 비용 단위를 읽기에서 **턴**으로 바꿔야 하는지 별도로 본다 |

**어느 쪽이든 `pWrong` 은 게이트로 안 돌아온다.** 이 측정은 문턱을 느슨하게 하거나
그대로 두거나이지, 엄격하게 만들지 않는다(오답 비용이 `1+n` 보다 클 수는 없다 —
후보가 n 개뿐이다).

## 비용

세션 수 = 5그룹 × 질의 3개 × reps 3 = **45세션**. `--budget` 으로 상한을 건다.
`rank.jsonl` 이 같은 코퍼스에서 45행이었으므로 규모는 검증된 범위다.

## 이 설계가 틀릴 수 있는 자리

- **`gold` 가 하나라고 가정한다.** 실제로는 답이 여러 문서에 걸칠 수 있고, 그러면
  "오답을 읽었다" 판정이 흔들린다.
- **ONAP 은 영어 코퍼스다.** 한국어 코퍼스에서 모델의 읽기 행동이 같다는 보장은 없다.
- **`reps 3` 은 변동을 잡기에 적다.** 하네스 주석이 "1 이면 통계를 못 낸다 — 변동이
  7배" 라고 적었다. 3 도 넉넉하지 않으므로 **분포를 보고 필요하면 늘린다.**
