# 한 이미지에 두 진입점 — 실행 전 설계 (2026-08-26)

## 무엇을 푸는가

서버 이미지를 배포해도 **저장소 clone 이 여전히 필요하다.** `cli/`(싱크·ACL 수집)가
이미지 밖에 있어서, 이미지를 받아도 **볼트를 만들 수 없다** — 서버는 읽기만 한다.
그래서 "이미지 배포" 가 얻는 것이 빌드 몇 분뿐이었다.

## 왜 지금까지 밖에 뒀나 — 그 이유는 유지한다

`compose.yml` 이 적어둔 것:

> `sync`·`acl` 은 Confluence 자격증명이 필요한데, **서버는 그걸 가질 이유가 없다**
> (가지면 "위키에 쓰기 금지" 가 설계 보장에서 규율로 내려간다).

**이것을 깨지 않는다.** 서버 프로세스가 자격증명을 갖는 순간, 읽기 전용은 *"우리는
안 쓴다"* 라는 약속이 되고 코드 리뷰로 지켜야 하는 것이 된다.

## 설계 — 배포 단위를 합치고 실행을 나눈다

한 이미지, 두 진입점:

```
docker run … wikilens serve      서버. 자격증명 없음. 볼트를 :ro 로 읽는다
docker run … wikilens sync       싱크. 자격증명을 받는다. 끝나면 종료
```

**보장이 유지되는 근거:** 자격증명은 이미지에 굽는 것이 아니라 `docker run` 시점에
주는 것이다. `serve` 로 뜬 컨테이너에는 애초에 없다 — 지금과 같다. 바뀌는 것은
"어디에 코드가 있느냐" 뿐이고 "누가 무엇을 들고 있느냐" 는 그대로다.

**`compose.yml` 의 서비스 정의도 그대로 둔다** — 거기에 자격증명 환경변수를 넣지
않는다. 넣는 순간 위 근거가 무너진다. `sync` 는 `docker compose run --rm` 이나
cron 이 부른다.

## 판정 기준 (실행 전에 고정)

- **`serve` 컨테이너에 자격증명이 안 들어간다** — `docker inspect` 로 환경변수를
  확인해 `CONFLUENCE_*` 가 없어야 한다. **계약으로 잠근다.**
- **clone 없이 볼트를 만들 수 있다** — 이미지만으로 `sync` → `build` 가 끝까지 돈다.
- **기존 사용법이 안 깨진다** — `docker compose up -d` 가 그대로 서버를 띄운다.
  진입점을 바꾸면서 기본 동작이 달라지면 쓰던 사람이 멈춘다.

## 대가 — 미리 적는다

- **이미지가 커진다.** Python 런타임과 의존성이 얹힌다(지금 449MB). JRE 가 이미
  대부분이라 비율로는 작지만 재는 것이 맞다.
- **서버만 띄우는 사람에게 안 쓰는 런타임이 들어 있다.** 공격면이 넓어진다 —
  이것이 이 설계의 유일한 실질적 손해이고, 대안(이미지 둘)을 버린 대가다.
- **빌드가 두 언어를 탄다.** Kotlin 빌드 스테이지에 Python 설치가 더해진다.

## 안 하는 것

- **서버가 sync 를 호출하게 만들기.** 그러면 보장이 깨진다. `serve` 는 끝까지
  Confluence 를 모른다.
- **자격증명을 이미지에 굽기.** 논외.
- **MCP 프록시를 넣기.** 그것은 사용자 머신에서 도는 플러그인이고 이미 배포돼 있다.
