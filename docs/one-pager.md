# WikiLens — 위키 탐색 오버레이

> **근거 표기** — ✓ 검증됨(계산 또는 문헌 확인) · ~ 확립된 관행(신규 주장 아님) · **?** 이 설계의 제안, **미검증**

**한 줄.** 사람 위키를 읽기 전용으로 미러링하고, 에이전트의 성공한 탐색 궤적을 축적해 다음 조회의 랭킹을 개선하는 레이어. 부산물로 위키 위생 보고서를 낸다.

**포지셔닝.** RAG로 분류하지 *않기를* 권한다. 분류상 주장이므로 반박 가능하지만, RAG라고 부르는 순간 벡터 DB·청킹·검색 정밀도 지표라는 반사가 따라오고 이 도메인에서는 그 반사가 어긋난다. 실제 차이: 반환값이 문서 내용이 아니라 좌표이고, 검색이 생성이 아니라 행동 선택을 조건화하며, 인덱스가 시스템 자기 동작의 산출물이다. 가까운 계보는 AWM(ICML 2025) ✓ 과 APC(NeurIPS 2025) ✓ 의 에이전트 메모리 계열. 엄밀히는 절차 기억보다 **일화 기억**에 가깝다.

**구현 상태.** Spring Boot 3.4 · Kotlin 2.1 · JDK 21 프로토타입 있음. **컴파일·실행 검증 안 됨.**

## 문제

에이전트는 세션 간 기억이 없다. 가중치(신피질)와 컨텍스트 윈도우(작업기억)는 있지만 일화 기억이 없어, 매 세션 같은 위키를 처음 보는 것처럼 재탐색한다.

위키에는 사람이 저작한 링크 그래프가 이미 있다. 그러나 링크를 그은 의도와 사람이 실제로 정보를 찾아가는 경로는 다르다. **? 이 격차에 활용 가능한 신호가 있다는 것이 이 설계의 핵심 가설이며, 아직 검증되지 않았다.**

## 아키텍처

| 레이어 | 내용 | 영속화 |
|---|---|---|
| **L0 미러** | 안정 페이지 ID, 사람 링크, 앵커 텍스트, ACL | 불필요 (재크롤) |
| **L1 색인** | BM25(본문) + 앵커 텍스트(고가중) + dense ~ | 불필요 (재구축) |
| **L2 학습** | 간선 가중치, 궤적 로그, 음의 간선 **?** | **궤적 로그 필수** |
| **보고서** | 누락 링크, 고아 페이지, 죽은 링크 | — |

L0/L1은 위키의 함수이므로 애매하면 버리고 다시 짓는다. **복구 불가능한 자산은 궤적 로그 하나뿐이다** — 간선 가중치는 궤적의 함수라 원리적으로 재집계 가능하지만, 비용 때문에 별도 보관하는 편이 낫다. 정밀 무효화는 이 둘에만 적용한다.

**~ 앵커 텍스트가 L1의 핵심.** 앵커는 대상 문서를 *출발지의 어휘로* 기술한다. 제목이 `OAuth 2.0 인가 코드 흐름`인데 열 개 페이지가 "로그인 방식"으로 링크했다면 그게 사용자의 실제 어휘이고 본문에는 없다. 어휘 불일치가 여기서 해소된다. 신규 기법이 아니다(Brin & Page 1998) — 그래서 신뢰도가 높고, **가치의 상당 부분이 L2가 아니라 여기서 나올 가능성이 크다.**

**APC 인용에 관한 단서.** APC의 핵심 발견은 키워드 매칭이 질의 임베딩 유사도보다 나았다는 것이지만 ✓, 그 우위는 코드 식별자의 정확 일치 성질에 의존한다. 위키 산문에는 이전되지 않으므로 이 설계는 계보만 인용하고 그 발견은 채택하지 않는다(dense 사용).

## 조회 경로

```
질의 → 경로 의존성 분류 → IDF 트리아지 → RRF 3랭커 융합 → 투기 점프 → 검증 → 폴백
```

**? 경로 의존성 분류 (미검증).** `LOCALIZATION`만 캐싱 가능. `TRACING`/`RATIONALE`은 경로가 곧 답이므로 압축하면 답을 삭제한다. 조회 경로에 LLM이 들어가면 아끼려던 비용을 되불러들이므로 어휘 규칙으로만 판정한다.
- 이 3분류 체계는 **이 설계의 발명이며 문헌 근거가 없다.**
- 어휘 규칙 분류의 정확도는 **측정된 바 없다.** 먼저 라벨링해 재야 한다.
- Minton(1988)의 효용 문제는 **유추로 인용한다.** 원 논문은 EBL 매크로의 *매칭 비용*이 절약을 잠식하는 문제이고, 여기서는 *LLM 추론 비용*이다. 구조적 논점은 같지만 직접 적용은 아니다.

**~ IDF 트리아지.** 매칭된 항의 최대 IDF를 진입점 신뢰도로 사용한다. 임계 미만이면 어휘 경로 실패로 보고 에이전트 탐색으로 넘긴다.

> **⚠ 임계값은 코퍼스 크기에 맞춰 캘리브레이션해야 한다.** BM25 IDF는 소규모 코퍼스에서 압축된다. 측정값 ✓ — 문서 4개면 `df=1` 항의 IDF가 1.204, 10개면 1.992. 임계를 1.6으로 고정하면 작은 위키에서 **모든 질의가 Diffuse로 빠진다.** 고정 상수로 두지 말 것.

**? 투기 점프.** 점프 후 검증, 실패 시 원본 궤적으로 폴백. 비용 비대칭(적중 = 수 초 절약, 실패 = 검증 1회)이 캐싱을 안전하게 만든다는 논리이지만, **이 도메인에서 정량화된 바 없다.**

## 학습 경로

궤적 보고 → `LOCALIZATION` 게이트 → **기존 저작 간선이면 가중치 강화, 없으면 에이전트 간선 신설** → Wilson 하한 갱신.

중복 간선을 만들지 않는 것이 핵심. 이렇게 하면 시스템이 "새 그래프 생성"이 아니라 **~ 저작된 그래프에 암묵적 피드백으로 랭킹을 학습**하는 것이 되고, 클릭 로그 기반 learning-to-rank라는 검증된 패러다임을 상속한다.

**~ Wilson 하한** — 단순 적중률은 1승 0패에서 1.0이 된다. 하한은 표본이 쌓이기 전까지 자동으로 비관적이다. 계산 확인 ✓: 1승 → 0.207, 4승 → 0.510, 9승 → 0.701. **다만 서빙 임계 0.45와 승격 임계 0.70은 임의 설계값이다.**

**~ 무효화**는 `pageId → shortcutIds` 역방향 포스팅으로. 포스팅 하나 조회 = 영향받는 숏컷 전체, 스캔 없음. 경유 노드 전원을 감시한다 — A→D가 성립한 근거가 경유 노드 B에 있었을 수 있다.

## 비목표

**✓ 파괴적 경로 압축 안 함.** 원본 궤적 보존. 의미적 유사성은 추이적이지 않다 — **정규화된 벡터에서** `cos(A,B)=cos(B,C)=0.8`이면 `cos(A,C)`의 하한은 `2(0.8²)−1 = 0.28`이고 이 하한은 실제로 달성 가능하다(계산 확인). 따라서 압축 간선이 "유사하다"를 주장하면 안 되고, 오직 "이 경로가 유용했다"만 주장한다.

**위키에 쓰지 않음.** 쓰면 사람 링크와 기계 링크가 섞여 정답 신호가 영구히 오염된다. 읽기 전용은 규율이 아니라 설계로 얻는 보장.

**일반화를 과신하지 않음.** 궤적 레이어는 논파라메트릭이므로 관측 궤적의 이웃 밖으로 못 나간다. 단 L1의 dense 검색이 임베딩 이웃까지는 메워주므로, "전혀 일반화하지 않는다"는 과한 표현이다.

## 측정

**1. ? 비링크 도달 비율 — 이 설계의 발명, 미검증.** 궤적 홉 중 사람 링크를 따르지 않은 비율. 낮으면 L2가 사람 그래프의 복사본으로 퇴화하고 기대 효용이 0에 수렴한다. 어휘 색인이 링크와 무관한 도달을 보장하는 게 유일한 탈출구.

> 이 지표를 킬 스위치로 제시하지만, **문헌 근거도 임계값 근거도 없다.** 유의미한 임계는 파일럿에서 직접 정해야 한다. 검증된 방법론으로 오인하지 말 것.

**2. ~ 시점 분할 홀드아웃.** 무작위 홀드아웃은 누출된다 — 링크 존재 시점의 궤적이 이미 그 링크를 담는다. T 시점 스냅샷 + T 이전 궤적으로 T 이후 신규 사람 링크를 예측. 베이스라인: Adamic-Adar, 공통 이웃(Liben-Nowell & Kleinberg 2007).

**3.** 적중률, 적중당 절약 대 미스당 검증 오버헤드, 간선 밀도.

## 구현 순서 (실패해도 산출물이 남게)

1. **L1만** 구축 → 검색 품질 측정. 가치의 대부분이 여기서 나올 가능성이 높다 (며칠)
2. **궤적 로깅만** 추가, 랭킹에는 미사용 → 비링크 도달 비율 측정 (몇 주)
3. 높으면 L2 활성화 / 낮으면 L2 폐기하고 **보고서 생성기로 전환**

## 적용 판단

**불필요한 경우 — 규모 임계.** 제목과 링크 그래프를 컨텍스트에 통째로 넣을 수 있으면 이 시스템 전체가 불필요하다. 임계는 평균 출력 차수에 매우 민감하다:

| 페이지 수 | 차수 5 | 차수 10 | 차수 25 |
|---|---|---|---|
| 1,000 | 28k | 48k | 108k |
| 10,000 | 280k | 480k | 1.08M |

위키는 차수 25도 드물지 않으므로, **자기 위키의 실제 평균 출력 차수를 먼저 재야 한다.** 이 임계선은 컨텍스트 윈도우가 커질수록 위로 올라간다.

또 위키가 잘 정리돼 있고 잘 안 바뀌면 사람이 쓴 인덱스 페이지가 더 낫다 — 더 정확하고, 비결정적이지 않고, 사람이 검증할 수 있다.

**? 필요 조건 (경험칙, 근거 없음).** 규모 임계 초과 · 높은 churn · 사내 은어와 제목의 괴리 · 분산된 핫셋 · 위키 위생 불량 · 다중 세션/에이전트. 세 개 이상 해당 시 구축 — **이 "세 개"는 임의 기준이다.**

## 미해결

- **ACL 필터링** — 공유 위키면 최우선. 문서만이 아니라 **간선과 앵커 텍스트까지** 필터링해야 한다. 페이지를 못 열어도 제목이 노출되면 유출이고, 간선의 존재 자체가 정보다. 현재 설계에 이 개념이 없다.
- **리비전 히스토리 가용성이 시점 분할 평가의 전제** ✓ — MediaWiki 완전, Confluence 버전 히스토리로 가능, **Notion은 앱 UI에만 있고 API로 노출되지 않는다.** Notion이면 2번 지표를 포기하거나 대체 설계가 필요하다.
- 사소한 편집 임계 — 오타 수정으로 궤적이 죽으면 안 된다. 구조 변경(제목/섹션/링크 집합)에만 반응하도록. **임계 미정.**
