# 앵커 층이 값어치를 하나 — 두 코퍼스 대조 (2026-08-23)

**형상** 서버 이미지 둘(`ANCHOR=4.0` 기본 · `ANCHOR=0.0` 대조) · **$0**(모델 없음).
코웨이 13,491건 30질의 · ONAP 15,493건 15질의. 실행 전에 예측을 못박았다
(`docs/design/design-2026-08-23-anchor.md`).

## 왜 쟀나

`CLAUDE.md` 가 랭킹 층 셋에 대해 **"셋 다 선택이고 각자 값어치를 증명해야 한다"**
고 선언했다. 학습 층은 증명됐다(D23·D26). **앵커는 한 번도 안 쟀다.**

한 코퍼스로는 "이 코퍼스에서는" 이라는 단서를 못 뗀다. 공개 코퍼스가 생겨
(D27) 처음으로 대조가 가능해졌다.

## 재는 법 — 가중만 끈다

앵커는 두 판에서 다르게 쓰인다: 로컬판은 스킬 절차의 **단계**, 서버판은 Lucene
**필드 가중**(`ANCHOR 4.0 · TITLE 3.0 · BODY 1.0`). 서버판을 잰다.

**색인은 안 건드린다.** 앵커 필드를 색인에서 빼면 색인 크기·분석 비용이 함께
바뀌어 다른 실험이 된다. 가중만 `0.0` 으로 둔 이미지를 따로 지었다.

## 결과 — 예측이 정반대로 틀렸다

```
              상위10 진입    못 찾음
  코웨이  켬     17/30         8
  코웨이  끔     13/30        15      ← 끄면 못 찾는 것이 거의 두 배
  ONAP   켬      8/15         4
  ONAP   끔      7/15         4      ← 거의 안 바뀐다
```

**예측은 반대였다.** "인링크가 3배 많은 ONAP(37%) 에서 앵커가 일하고, 코웨이(12%)
에서는 거의 안 바뀔 것" 이라고 적었다. 실측은 그 반대다.

### 가르는 것은 인링크 비율이 아니라 어휘 격차다

코웨이에서 크게 갈린 그룹:

```
  G02  [4, 3, -1] → [-1, -1, -1]      앵커 없으면 통째로 실종
  G03  [-1, 9, -1] → [-1, -1, -1]
  G09  [14, 24, 22] → [14, -1, -1]
```

**질의가 문서에 없는 말을 쓸 때 앵커가 유일한 다리다.** 코웨이 질의는 구어체
한국어라 제목·본문 어휘와 어긋나는데, 다른 문서가 그 문서를 부른 말이 앵커에
남아 있다. ONAP 질의는 영어이고 문서 어휘를 상당히 공유해서(`committer`·`CI
chain`·`DMaaP`) 다리가 필요 없다.

별칭 비율은 두 코퍼스가 비슷하다(앵커 대비 24% 대 28%). 인링크 보유만 3배
다른데 효과는 반대 방향이니, **인링크 수가 예측 변수가 아니다.**

## 같은 층이 양방향으로 작동한다 — G05

```
  G05  [10, 8, 13] → [1, 1, 1]        앵커를 끄니 정답이 1위
```

앵커가 **정답을 8위 밖으로 밀어내고 있었다.** 원인을 열어 보니 분명하다:

```
  정답 286067130   indeg=28   앵커 28개 전부 "Wiki 참조"
  오답 286066505   indeg=1    앵커 1개  "26.01 정보 보안 개선 조치"(제목 그대로)
```

정답은 28곳에서 링크됐는데 **전부 내용 없는 낱말**이라 앵커 필드에 질의 항이
하나도 없다.

> **여기서 인과를 틀리게 적었다 — 2026-08-26 에 재서 정정한다.**
>
> 처음에는 "정답만 최대 가중 필드에서 0점이 되어 **밀려난다**" 고 썼다. 검증하려고
> 정답의 무의미 앵커 29개를 **실제로 지우고** 다시 색인했더니 순위가 `[10, 8, 13]`
> 그대로였다. 지울 게 없었던 것이다 — 그 필드는 이미 0점이었다.
>
> **정답이 잃은 것이 아니라 오답이 벌고 있었다.** 오답의 앵커 `26.01 정보 보안
> 개선 조치` 가 질의의 `보안`·`조치` 와 맞아 최대 가중으로 점수를 받는다. 그래서
> 앵커 가중을 **통째로 0** 으로 만들어야만 뒤집힌다:
>
> ```
>   기준선(앵커 4.0)      286066505 | 355831880 | 173702876
>   무의미앵커만 제거      286066505 | 355831880 | 173702876   ← 기준선과 같다
>   앵커 가중 0          **286067130** | 286001822 | 248545544
> ```
>
> 방향은 같지만 **고칠 자리가 다르다.** "정답의 앵커를 청소하면 된다" 가 아니라
> "앵커가 오답에 유리하게 걸릴 때가 있다" 이고, 후자는 목록으로 못 고친다.

**이것이 D26 의 미해결을 설명한다.** 거기서 대조군 5/6 이 `286066505` 를 골랐고
"어휘 층이 구조적으로 그것을 위에 둔다" 까지만 적었는데, 그 구조가 앵커 가중이다.

### 다만 드문 현상이다

```
  코웨이  앵커 4,339개 중 무의미 38 (0.9%) · 앵커가 전부 무의미한 페이지 4/1,655
  ONAP   앵커 31,490개 중 무의미 60 (0.2%) · 전부 무의미한 페이지 11/5,763
```

**빈도는 낮은데 걸리면 치명적이다.** `Wiki 참조` 29회 중 28회가 G05 정답 하나에
몰려 있다.

## 그래서 판정 기준이 바뀐다

```
  전  인링크가 많은 코퍼스에서 값어치가 있다      ← 예측, 틀렸다
  후  질의와 문서의 어휘가 어긋날 때 값어치가 있다  ← 실측
```

코웨이 총합(17 대 13)은 **어휘 격차를 메우는 쪽이 밀어내는 쪽을 이긴 결과**이지,
앵커가 항상 돕는다는 뜻이 아니다.

## 양방향의 실제 비율 — 16 대 4 (2026-08-26)

"같은 층이 양방향으로 작동한다" 를 사례 하나(G05)로만 적어 뒀다. **코웨이 30질의를**
하나씩 대조해 방향을 셌다($0, 상위 50까지 봐서 `밖` 을 줄였다). **ONAP 에서는 안 쟀다** —
거기서는 켬/끔 총합이 8 대 7 이라 방향을 세도 표본이 너무 작다:

```
  앵커가 도운 것   16건    그중 **밖 → 안으로 건진 것 6건**
  앵커가 해친 것    4건    그중 **안 → 밖으로 죽인 것 0건**
  안 바뀐 것       10건
```

건진 여섯(`-1 → 안`): G02q1 · G03q0 · G03q2 · G06q1 · G09q1 · G09q2.
**앵커가 없으면 아예 못 찾던 질의들이다.**

해친 넷 중 **셋이 G05 한 그룹**이고(`10→1`·`8→1`·`13→1`), 나머지 하나는
G09q0 의 `15→14` 로 사실상 잡음이다. 즉 **문서 하나가 만든 문제**다.

### 그래서 가중을 낮추지 않는다

`ANCHOR = 4.0` 을 낮춰볼까 했다. 이 비율이 그 판단을 정한다:

- **죽인 것이 0건이다** — 앵커가 정답을 결과 밖으로 밀어낸 적이 없다
- **건진 것이 6건이다** — 그 구조가 곧 이 층의 존재 이유다
- 해침은 **순위 하락일 뿐**이고 한 그룹에 몰려 있다

가중을 낮추면 **여섯을 약하게 만드는 대가로 하나의 하락을 완화**하는 거래다.
`RRF_K` 를 안 잠근 것과 같은 이유로 **측정 없이 굳히지 않되, 이 측정은 낮출
근거가 없다고 말한다.**

**남은 것:** 스윕(1.0·2.0·3.0)은 안 돌렸다. 코퍼스가 둘이라 한쪽에서 고르고
다른 쪽에서 확인하는 방식이 가능해졌지만, 위 비율을 보면 얻을 것이 적다.

**그리고 이 값의 근거가 저장소 어디에도 없다.** `FieldBoost.kt` 의 주석은 순서만
말하고("앵커 > 제목 > 본문"), 최초 커밋부터 `4.0` 이 유도 없이 들어 있다. 그래서
이 문서도 한때 "손으로 정한 값" 이라고 적었는데 **그것은 확인되지 않은 단정이었다** —
값의 출처를 모르는 것과 손으로 정해진 것은 다르다. 근거를 아는 사람이 그 자리를
채울 것. `조용히 실패 28`(근거가 적힌 자리에 상수를 둔다)이 가리키는 자리다.

## 계층 층(`TREE.md`)도 함께 쟀다 — 재는 법부터 틀렸다 (2026-08-26)

앵커와 같은 방법("가중을 꺼서 대조")으로 재려 했는데 **끌 가중이 없다.** 실측:

```
  SearchService = 어휘(RRF_K=60) + 학습 힌트(LEARNED_WEIGHT=1.6)
  계층은 랭킹에 안 들어간다 — `tree` 도구와 로컬판 스킬 단계에서만 쓰인다
```

그래서 질문이 달라진다. **"순위를 좋게 하나" 가 아니라 "없으면 무엇을 못 하나" 다.**

### 로컬판 — 두 코퍼스 모두 적중 0건

`rank.py` 가 적중 단계를 기록하므로 **재실행 없이 읽힌다**:

```
  코웨이 30질의   ALIASES 6 · TREE 0 · BODY 5   (적중 11)
  ONAP  15질의   ALIASES 3 · TREE 0 · BODY 4   (적중 7)
```

**`TREE` 단계가 한 번도 답을 준 적이 없다.** 원인은 파일이 아니라 중복이다:

```
  TREE 제목이 ALIASES 에도 있는 비율   코웨이 99% · ONAP 99%
  TREE 에만 있는 것                    1건 · 15건
```

`ALIASES.md` 가 **제목의 상위집합**(제목 + 별칭)이라, 앞 단계에서 안 잡힌 것이
뒤 단계에서 잡힐 여지가 원리적으로 거의 없다. `CLAUDE.md` 가 "ALIASES 는 TREE 의
상위집합" 이라고 적어둔 것이 실측으로 확인됐다.

### 그래도 지우지 않는다

`TREE.md` 는 **검색 단계가 아니라 `tree` 도구**의 자료다. 목차를 훑어 내려가는
사용에는 그것뿐이고, 그 값어치는 순위로 못 잰다 — 에이전트가 부르는지, 불러서
답에 닿는지는 세션을 태워야 나온다($). **이번에는 안 쟀다.**

**로컬판 스킬 절차에서 `TREE` 단계를 뺄지는 별도 판단이다.** 적중 0건이지만
비용도 0 에 가깝고(`grep` 한 번), 빼면 "영역만 알 때 위에서 내려가기" 라는 경로가
사라진다. 그 경로를 실제로 쓰는지는 안 쟀다.

## 이 측정이 증명하지 못하는 것

- **질의가 45개뿐이다.** 상위 10 진입이 한둘 갈리는 것으로 결론을 내면 안 된다.
  코웨이의 17 대 13(못 찾음 8 대 15)은 폭이 크지만 ONAP 의 8 대 7 은 아니다.
- **두 코퍼스가 언어까지 다르다.** 어휘 격차와 언어를 갈라내지 못했다. 같은
  언어의 두 코퍼스로 재야 "격차" 가 원인이라고 단정할 수 있다.
- ~~**무의미 앵커를 거르면 나아지는지는 안 쟀다.**~~ **쟀다(2026-08-26) — 값어치가
  없어서 안 넣는다.** **코웨이** 볼트 사본에서 무의미 앵커 40개를 걸러 재색인했더니
  상위10 진입이 `17/30 → 17/30`, 못 찾음이 `9 → 9` 로 **아무것도 안 바뀌었다**
  (달라진 것은 G09 한 질의의 `15위 → 14위` 뿐). 손으로 정한 불용어 목록을
  유지하는 비용만 남으므로 넣지 않는다.
- **양방향 비율(16 대 4)과 거르기 결과는 코웨이 한 코퍼스다.** 켬/끔 총합만 두
  코퍼스에서 쟀고, 그 아래 세부는 전부 코웨이다. ONAP 에서 같은 비율이 나오는지는
  모른다 — 오히려 거기서는 앵커 효과 자체가 거의 없었으므로 다를 가능성이 높다.
- **로컬판은 따로다.** 여기서 잰 것은 서버판의 필드 가중이다. 로컬판의 `ALIASES`
  단계 값어치는 `rank.py` 가 단계를 기록하므로 별도로 읽어야 한다.
