# 서버판 로컬 실행

로컬판(볼트 + 별칭 색인) 위에 **얇은 경험 공유 서비스**를 얹습니다.

## 서버가 하는 일과 안 하는 일

```
저장:  term       → {page_id: (hits, misses)}
       trajectory (session, keywords, read page_ids, success)
```

**콘텐츠·제목·경로·앵커를 저장하지 않습니다.** 색인·토큰화·랭킹은 전부 클라이언트가
자기 볼트에 대해 수행합니다. 서버는 **혼자서는 모을 수 없는 통계**만 모읍니다.

이 결정이 ACL 문제 대부분을 없앱니다. 서버가 페이지 ID를 반환해도 클라이언트가
자기 볼트에 없으면 조용히 버립니다 — 볼 수 없는 문서는 애초에 볼트에 없으니까요.
서버는 그 페이지의 제목도 모르므로 제목 유출 경로도 없습니다.

## 한 번에 확인하기

```bash
python demo_server.py
```

볼트 생성 → 서버 기동 → 세션 시뮬레이션 → 힌트 발동 → 게이트 검증까지
자동으로 돕니다. 실제 훅 스크립트를 실제 페이로드 형식으로 호출하므로,
이게 통과하면 실제 Claude Code 연동도 동작합니다.

## 수동 실행

**터미널 1 — 서버**

```bash
wikilens serve --port 8787 --state ./.wikilens-server
```

**터미널 2 — 검색**

```bash
wikilens --root ~/wiki search "로그인 붙이는 법" --server http://127.0.0.1:8787
```

```
[Confident] 최대 IDF 2.31 / 임계 1.85 · 로컬 후보 12 · 서버 힌트 1

 * 1. OAuth 2.0 인가 코드 흐름 rel=0.74
      mirror/pages/30/00/300000001.md
   2. 신규 입사자 FAQ
      mirror/pages/30/00/300000006.md

  * = 로컬과 서버 양쪽, S = 서버 힌트만
```

**Claude Code 연동**

```bash
export WIKILENS_SERVER=http://127.0.0.1:8787
cd ~/wiki && claude
/plugin marketplace add ./path/to/marketplace
/plugin install wikilens@wikilens-tools
/reload-plugins
```

플러그인이 스킬(검색 순서 안내)과 훅(관측)을 함께 설치합니다.

## 훅 동작

| 이벤트 | 하는 일 |
|---|---|
| `UserPromptSubmit` | 질의를 로컬 버퍼에 append |
| `PostToolUse(Read)` | 볼트 안 파일이면 **페이지 ID만** 추출해 append |
| `SessionEnd` | 버퍼를 서버로 일괄 전송 후 삭제 |

**에이전트에게 아무것도 요청하지 않습니다.** 네이티브 Read 호출을 관측할 뿐입니다.
"작업 보고" 성격의 도구는 에이전트가 안정적으로 호출하지 않으므로, 관측이 유일하게
신뢰할 수 있는 방식입니다.

Read는 핫 패스라 매번 네트워크를 타면 세션이 느려집니다. 로컬 파일에 한 줄 append만
하고(측정값 약 63ms, 대부분 파이썬 기동 비용) 종료 시 일괄 전송합니다.
볼트 밖 파일은 아예 기록하지 않습니다.

## 신뢰도: Empirical Bayes

Wilson 하한은 카운트만 봅니다. 같은 4승 3패라도 로컬 검색이 강하게 가리키는 후보와
겨우 걸린 후보를 구분하지 못하죠. 클라이언트의 로컬 점수를 **사전분포**로 쓰면
그 정보가 살아납니다.

```
prior = Beta(s·κ, (1−s)·κ)          s = 정규화된 로컬 검색 점수
post  = Beta(s·κ + hits, (1−s)·κ + misses)
신뢰도 = post의 5% 분위수
```

| 전적 | 사전 0.85 | 사전 0.30 |
|---|---|---|
| 1승 0패 | 0.616 | 0.128 |
| 5승 0패 | 0.761 | 0.396 |
| 15승 0패 | 0.878 | 0.672 |

사전분포는 데이터가 없을 때만 일합니다 — 400승 300패에서 격차가 0.005로 사라집니다.
그래서 탐색을 위해 서빙 품질을 희생할 필요가 없습니다.

사전확률은 `[0.05, 0.85]`로 클램프합니다. 1.0을 허용하면 Beta의 한쪽 모수가 0이 되어
**한 번 관측에 신뢰도 1.0**이 나옵니다(실제로 겪은 버그).

## 지표

```bash
curl -s localhost:8787/stats | python -m json.tool
```

| 지표 | 의미 |
|---|---|
| `p_wrong` | **가장 중요.** 손익분기 `p_hit > p_wrong/(n−1)`의 분자 |
| `ambiguous_keys` | 같은 항에 목적지가 여럿 — 질의가 모호한 경우 |
| `keys` / `key_page_pairs` | 학습된 포스팅 규모 |

적중률이 아니라 **오답률**이 기준입니다. 캐시가 확신 없을 때 침묵하면
`p_wrong → 0`이 되어 거의 항상 이득입니다. EB 게이트가 하는 일이 그것입니다.

## 개발 중 실제로 겪은 버그

회귀 테스트로 잠가뒀습니다(`tests/test_server.py`).

| 버그 | 증상 | 원인 |
|---|---|---|
| 항이 안 겹침 | 힌트가 항상 0건 | 클라이언트는 바이그램, 서버 폴백은 단순 분리 |
| 카운트 분산 | 5세션인데 서빙 안 됨 | 키워드 **집합**을 키로 씀. 항 단위 포스팅이어야 |
| 즉시 만점 | 1관측에 rel=1.00 | 사전확률 1.0 → Beta 모수 0 |
| 이중 확정 | 궤적이 3건 기록 | `on_query`와 `on_end`가 같은 스팬을 확정 |
| 분류 오탐 | "배포 파이프라인 어디"가 TRACING | 도메인 명사를 흐름 마커로 씀 |
| 조회 누락 | "…알려줘"가 UNKNOWN | 위치 명사만 마커에 있고 조회 동사가 없음 |

## 아직 미해결

**"유용했다"의 판정.** 훅은 무엇을 읽었는지만 보여줍니다. 지금은 두 가지 약한 신호를
씁니다 — 마지막으로 읽은 페이지가 답일 확률이 높다, 키워드가 겹치는 질의가 뒤따르면
앞 시도는 실패였다(재구성 신호). 웹 검색의 abandonment 신호와 같은 구조이고
마찬가지로 노이즈가 있습니다. `p_wrong`이 그 노이즈의 크기입니다.

**질의 키워드는 서버로 갑니다.** 콘텐츠는 아니지만 질의어 자체가 민감할 수 있습니다.
클라이언트가 IDF 낮은 흔한 항을 걸러 보내지만 완전한 해결은 아닙니다.

**한국어 토큰화가 근사입니다.** 문자 바이그램으로 조사를 흡수합니다.
`kiwipiepy`로 교체하려면 `wikilens/tokenizer.py` 하나만 바꾸면 되지만,
**클라이언트와 서버를 동시에** 바꿔야 합니다. 다르면 조용히 0건이 됩니다.
