> **B 는 MCP 가 아니다.** 로컬판의 정의적 성질이 "검색 경로 런타임 의존성 0" 이라

## 재는 장치가 둘이다 — 축이 다르다

**나란히 놓고 비교하지 말 것.** `rank.py` 는 순위를, `agent.py` 는 실제 비용을 잰다.

### `rank.py` — 순위만, $0

정답이 **몇 위**에 오나. 로컬판은 스킬 절차(ALIASES → TREE → 본문)를 밟고 **어느
단계에서 찾았는지** 남긴다. 틀렸을 때 **무엇을 대신 골랐는지**가 랭킹 진단의 단서다.

```bash
python3 bench/rank.py
```

**비용은 안 잰다.** 예전에는 여기서 문자 수·지연도 쟀는데, 그것은 내가 가정한 접근
패턴이지 측정이 아니었다. `agent.py` 옆에 같은 표 모양으로 놓이니 **4자리 차이 나는
지연(8ms 대 73,000ms)을 비교로 읽게** 됐다. 흉내는 걷어내고 실측만 남겼다.

**A 원시 grep 은 대상이 아니다** — 랭커가 없어 순위라는 개념이 없다.

### `agent.py` — 진짜 세션

`claude -p` 로 **케이스마다 독립된 Claude Code 세션**을 띄운다. 실제 토큰 수(`usage`)와
비용(`total_cost_usd`)이 나온다.

```bash
bench/setup.sh up
python3 bench/agent.py          # 기본이 최소 집합 — 9세션 약 $5
bench/setup.sh down
```

**기본값이 최소다.** 세션당 $0.5~1.6 이라 전량(90세션)은 켜야 나간다.

| | 세션 | 대략 |
|---|---|---|
| 기본 (`MINIMAL` 3그룹 × q0 × 1회) | 9 | $5 |
| `--per-group 0` (그룹당 3질의) | 27 | $14 |
| `--groups G01 … G10 --per-group 0 --reps 3` | 81 | $43 |

**순위를 여기서 재지 말 것.** `rank.py` 가 30질의 전량을 $0 에 낸다. 세션이 유일하게
주는 것은 **에이전트가 실제로 얼마나 일하나**이고, 그건 그룹 셋이면 모양이 다 나온다.
**정본은 `queries.py` 의 `MINIMAL` 이고 여기 옮겨 적지 않는다** — 고른 근거를 그 옆에
적어 두었고, 한 번 여기 복제했더니 그룹을 바꾼 뒤 이 줄만 낡았다.

**`--reps 1` 은 통계를 못 낸다** — 변동이 7배다. 리포트가 표본 부족을 스스로 찍는다.
우열을 주장하려면 반복을 올려야 하고, 그건 비용을 올린다는 뜻이다.

**중단돼도 이어받는다** — 끝난 조합은 건너뛴다(워밍과 실패는 안 센다). `--budget` 이
USD 상한이고 **워밍도 그 예산을 쓴다.** `--warmup` 은 케이스마다 버리는 1회를 먼저
돌려 **MCP 첫 호출 오버헤드**를 분리한다 — 첫 세션만 유독 비쌀 수 있는데, 버리는
1회를 따로 기록해 두면 그것이 기동 비용인지 확인된다.

### 케이스 격리 — `setup.sh` 가 설치본을 내린다

`--plugin-dir` 는 플러그인을 **추가**할 뿐 사용자 레벨 설치본을 끄지 않는다. 설치본이
있으면 세 케이스가 서로의 것을 본다(전부 실측):

| | 보면 안 되는 것 | 안 막으면 |
|---|---|---|
| A | wikilens-local · wikilens-client | 로컬 스킬이 `config.json` 의 **진짜 볼트**를 가리켜 격리가 경로로 우회된다 |
| B | wikilens-client | **B 가 MCP 를 쓴다** — B 와 C 가 같은 것을 재게 된다(실제로 그랬다) |
| C | wikilens-local | MCP 대신 grep 을 쓸 수 있다 |

**도구 이름으로는 못 막는다** — `Skill(이름)` 형식이 안 먹고, `Skill` 통째로 막으면
B·C 가 자기 스킬을 못 쓴다. `setup.sh up` 이 설치본을 내리고 `--plugin-dir` 만
남긴다. 그러면 각 세션이 자기 플러그인만 본다:

```
A 원시grep   Bash 만
B 로컬판     Skill + Bash + Read
C 서버판     mcp__plugin_wikilens-client_wiki__* (search·read·grep·tree·answer)
```

**`down` 이 되돌린다 — 벤치가 죽으면 안 돌아오므로 끝나면 반드시 부를 것.**
도구 이름은 매 측정에 기록되므로, 격리가 깨지면 결과 파일에서 바로 보인다.

**권한도 벤치가 스스로 정한다.** 개발자 머신의 `.claude/settings.local.json` 에는
대화 세션에서 하나씩 승인된 도구가 누적돼 있고 `claude -p` 가 그것을 상속한다 —
**새 MCP 도구를 추가하면 벤치에서만 조용히 거부된다.** 실제로 겪었다: 모델이
`answer` 를 부르는데 서버 진술이 계속 0 이었고, 도구 **응답**을 기록하기 전까지
원인이 안 보였다(`Claude requested permissions … but you haven't granted it yet`).
`case_c` 가 `--allowedTools` 로 MCP 서버를 통째로 허용해 그 의존을 끊는다.

### 실험이 둘이다 — cold 와 warm

```bash
bench/setup.sh up cold    # 궤적 비움 (기본)
bench/setup.sh up warm    # 궤적 유지
```

**궤적을 비울지가 곧 무엇을 재느냐다.**

| | 재는 것 |
|---|---|
| **cold** | **검색 엔진 자체** — BM25+앵커 대 grep. 학습이 없어 셋이 같은 출발선 |
| **warm** | **학습이 값어치를 하나** — 회차가 갈수록 C 가 나아지는지 |

**둘 다 필요하다.** warm 만 재면 서버판이 이겨도 그것이 형태소 분석 덕인지 학습 덕인지
못 가린다. **cold 와의 차이가 곧 학습의 기여분**이다.

서버판의 존재 이유가 "세션을 넘어 쌓이는 학습" 이므로 cold 만 재면 **C 를 절반만 재는
것**이다. 반대로 warm 은 **비대칭**이다 — C 만 이전 회차를 물려받고 A·B 는 매번
처음부터다. 그것이 학습 층의 설계 그대로지만(A·B 에는 학습이 아예 없다) 리포트가
그 사실을 밝힌다.

**모드는 서버에 물어 기록한다** — 플래그로 받으면 cold 로 띄워놓고 warm 이라 적는 일이
생긴다. 매 측정에 그 시점의 궤적 수가 남고, `report.py` 가 그것으로 학습 곡선을 낸다.

### warm 에서 질의 순서가 곧 가설이다 — `--pattern`

```bash
python3 bench/agent.py --pattern repeat --reps 5 --groups G04 --per-group 1
python3 bench/agent.py --pattern transfer --reps 5 --groups G04
```

| | 순서 | 재는 것 |
|---|---|---|
| `spread`(기본) | q0,q1,q2 × N | 섞여서 원인 분리가 안 된다 |
| `repeat` | q0×N, q1×N, q2×N | **정확 반복** — c=1.0 이라 발동해야 한다 |
| `transfer` | q0 를 N−1회 학습 → q1,q2 시험 | **표현 전이** — c 가 낮아 안 될 것이다 |

### 케이스를 하나만 돌릴 때 — `--cases`

```bash
python3 bench/agent.py --cases C --groups G09    # C 만
```

**세 방식 비교에는 셋이 다 필요하다.** 하나만 쓰는 것은 *그 방식 안에서* 무언가를 잴
때다 — 예를 들어 서버 궤적의 `dest` 추정은 A·B 가 서버를 안 쓰므로 잴 대상이 아니다.
처음에 그것을 모르고 전량을 돌려 A·B 세션을 통째로 버린 적이 있다.

## 권장 흐름 — cold 와 warm 을 한 표에서 보기

```bash
# ① 학습이 발동하는지부터 $0 로 (서버만 띄운다 — 플러그인 안 건드림)
bench/setup.sh server cold
python3 bench/learn.py --pattern repeat
python3 bench/learn.py --pattern transfer

# ② cold — 검색 엔진 자체
bench/setup.sh up cold
python3 bench/agent.py                                    # 9세션 ~$5

# ③ warm — 학습까지. ②가 만든 궤적을 물려받는다
bench/setup.sh up warm
python3 bench/agent.py --pattern repeat --reps 3 --groups G04 --per-group 1

bench/setup.sh down                                       # 플러그인 복구
python3 bench/report.py
```

**①을 먼저 하는 이유:** 서빙이 0 인 채로 세션을 태우면 "학습이 행동을 안 바꿨다" 와
"애초에 학습이 없었다" 가 구별되지 않는다. $0 이므로 안 할 이유가 없다.

**③에서 `--groups G04` 로 좁히는 이유:** ②가 만드는 궤적은 그룹당 **1건**뿐이라
그것으로 힌트가 서빙되는 그룹이 G04 하나다(실측, `learn.py`). 나머지 둘은 warm 이어도
cold 와 같은 값이 나와 세션만 태운다. `repeat 3회`로 몰아주면 **회차별 곡선**이 나온다.

**같은 파일(`agent.jsonl`)에 이어 써도 된다.** `mode` 가 키에 들어 있어 cold 와 warm 이
안 섞인다 — 예전에는 `done_keys` 가 warm 을 통째로 건너뛰거나, 파일을 나눠도
`report.collect` 가 **cold 를 warm 으로 덮었다**(먼저 잰 쪽이 리포트에서 사라졌다).

리포트의 **`학습 기여분 (cold ↔ warm)`** 절이 둘을 나란히 낸다:

```
  A 원시grep     cold 0/3 · 1,200,000tok  warm 0/3 · 1,180,000tok
  B 로컬판        cold 0/3 ·   450,000tok  warm 0/3 ·   460,000tok
  C 서버판        cold 0/3 ·   320,000tok  warm 3/3 ·   180,000tok

  대조군(A·B) 변동 2% 보다 C 의 44% 가 크다 — 학습 기여로 읽을 여지가 있다
```

**A·B 가 대조군이다.** 둘에는 학습이 아예 없으므로 cold 와 warm 이 같아야 한다.
거기서 차이가 나면 학습이 아니라 **측정 변동**을 보는 것이고, 그 폭이 C 의 차이보다
크면 C 의 차이도 못 믿는다. 리포트가 그 판정을 대신 한다.

## 질의 — `queries.py`

10그룹 × 3질의. **같은 답을 내야 하는 유사 질의**를 묶었고, 코퍼스를 직접 읽어
사람이 치는 말로 썼다. 설계 근거와 함정은 그 파일의 독스트링에 있다.

30개 전량은 `rank.py`($0)가 쓰고, **`agent.py` 는 그중 `MINIMAL` 세 그룹만** 쓴다.
비싼 쪽에만 최소를 적용하는 것이라 순위 데이터는 안 줄어든다.

**순위로 질의를 고르지 않았다** — 랭커에 맞춰 시험지를 고치면 순환 논리가 된다.

## 이 하네스 자체의 테스트

```bash
python3 -m pytest bench/tests -q        # `./check.sh` 가 함께 돌린다
```

**순수 함수만 덮는다** — 키 충돌 · 요약 통계 · `plan()` 순서 · `mode_split` 의 공통
질의 필터 · `collect` 가 `stale-*/` 를 안 걷는지. `probe`·`run_once` 처럼 서버가
필요한 것은 안 덮는다(테스트가 환경에 매달리면 `check.sh` 가 못 돈다).

여기서 잡은 결함이 하루에 넷이었다 — cold/warm 키 충돌 · `mode_split` 이 다른 시험지를
비교 · `transfer --reps 2` 가 학습 0회 · read 실패 시 세션 미종료. 전부 조용한 종류라
**결과 표가 그럴듯하게 나오는 것으로는 안 잡힌다.**

## 결과 해석에서 조심할 것

**변동이 크다.** 같은 조건을 반복해도 토큰이 배수로 흔들리고, 그 폭이 케이스 간
차이보다 클 수 있다 — **단발 측정으로 우열을 주장하면 안 된다.** 리포트가 IQR 겹침을
스스로 지목하므로 그 판정을 따를 것.

**쉬운 그룹은 변별하지 못한다.** 세 방식이 다 맞히면 돈만 쓰고 정보가 없다 —
`MINIMAL` 기본값이 그래서 셋뿐이다. 그룹을 늘릴 때도 `rank.py` 로 먼저 순위를 보고
**갈리는 그룹**부터 고를 것.

**궤적이 쌓인다.** C 케이스는 MCP 프록시가 `sessionId` 를 보내므로 질의가 학습으로
기록된다. `setup.sh` 가 전용 서버를 띄우는 이유이고, **운영 서버로 돌리면 안 된다.**

## 형상 — 어느 코드에서 잰 값인가

측정마다 **커밋(또는 태그)과 더러운 트리 여부**를 남긴다. 결과만 남고 코드가 바뀌면
그 수치는 복원 불가가 된다 — 이 저장소가 `13,921건 2.44초` 로 한 번 겪은 일이다.

```
=== 형상 ===
  bench-baseline-<날짜>                                  90건
  a1b2c3d4 (dirty)                                       9건
  ★ 형상이 섞여 있다 — 코드가 바뀐 전후를 한 표에 넣고 있다
```

**더러운 트리는 표시한다** — 커밋 해시만 남기면 "그 커밋에서 나온 값" 처럼 읽히는데
사실이 아니다. C 케이스는 **서버 이미지 ID** 도 남긴다: 소스를 고치고 다시 안 지으면
옛 이미지가 도는데(실제로 겪었다), 커밋만으로는 그것을 못 잡는다.

**그리고 `setup.sh` 가 띄우기 전에 빌드한다.** 기록만으로는 부족했다 — 이미지 ID 가
결과에 남아도 그걸 보는 것은 **돈을 쓴 뒤**다. 실제로 그렇게 한 번 물렸다(2026-08-14:
새 지표가 `/api/stats` 에 아예 안 나왔고, 7시간 전 이미지가 돌고 있었다). 빌드가
실패하면 거기서 멈춘다 — 옛 이미지로 재는 것보다 안 재는 편이 낫다.

기준 태그는 `bench-baseline-<날짜>` 꼴이다(`git tag` 로 확인).
**옮기지 말 것** — 코드가 바뀌면 새로 단다. 옮기면 옛 결과가 어느 형상에서 나왔는지
복원할 수 없다. **어느 것이 최신인지도 여기 적지 않는다** — 태그가 늘 때마다 낡는다.

## 결과 보기

```bash
python3 bench/report.py                    # 표
python3 bench/report.py --md               # 붙여 넣을 마크다운
```

**파일로 떨궈 저장소에 두지 말 것.** 그러면 그것이 "손으로 옮겨 적은 표" 와 같아진다 —
데이터는 바뀌는데 파일은 안 바뀐다. 공유할 일이 있으면 그때 출력을 붙여 넣고, 저장소에는
`results/*.jsonl` 만 남긴다(그것도 gitignore 대상이다).

**손으로 옮겨 적은 표는 두지 않는다.** 그렇게 했더니 질의를 바꾼 순간 문서가 조용히
낡았다 — 질의 4개가 전부 교체됐는데 문서는 옛 값을 말하고 있었다. `results/*.jsonl`
이 정본이고 표는 거기서만 나온다.

리포트가 **말할 수 없는 것을 스스로 말한다:**

- 토큰은 **IQR 겹침** — 겹치면 우열을 주장할 수 없다
- 적중률은 **Wilson 95% 구간** — 비율이라 IQR 이 안 맞는다. 같은 쌍인데 토큰은
  겹치고 적중률은 갈리는 일이 있고, 그때 한쪽만 보면 틀린 결론을 낸다
- **형상·모델·코퍼스가 섞이면** 지목한다 — 코드가 그대로여도 모델이 바뀌면 다른 실험이다
- **격리 검증** — 케이스가 쓰면 안 되는 도구를 썼거나(누출), 반드시 써야 하는 도구를
  한 번도 안 썼으면(C 가 MCP 를 안 씀) "이 측정은 무효" 라고 찍는다

**격리 검증이 실제로 무효를 잡은 적이 있다.** 초기 파일럿이 `--plugin-dir` 만 믿고
설치본을 안 내려서 B 가 C 의 MCP 도구를 썼고, 결과 파일의 도구 이름으로 그것이
드러났다. 그때 만든 대응이 `setup.sh` 의 설치본 내리기다 — 위 "케이스 격리" 절.
샘플 결과 파일은 남기지 않는다(측정값이 낡으면 그 자체가 함정이 된다).
