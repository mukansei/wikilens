# eval — 검색 방식 비교

**이것은 지워진 `bench/` 가 아니다.** 그쪽은 합성 코퍼스 시뮬레이션이었고, 절대 수치를
믿을 수 없어 2026-08-04 에 제거됐다(`DECISIONS.md` D1 참고). 여기는 **실제 코퍼스
13,933건**에서 재고, 에이전트 벤치는 **실제 Claude Code 세션**을 띄운다. 이름을 달리
쓰는 이유가 그것이다 — 한 단어가 두 물건을 가리키면 안 된다.

세 방식을 비교한다:

| | 무엇 | 어떻게 격리하나 |
|---|---|---|
| **A 원시 grep** | 안내 없이 볼트를 훑는다 | `ALIASES.md`·`TREE.md` 가 **없는** 볼트를 준다 |
| **B 로컬판** | 스킬 + 네이티브 grep | `--plugin-dir plugin/local` |
| **C 서버판** | MCP 도구 4개 | `--plugin-dir plugin/client` + 전용 서버 `:8790` |

> **B 는 MCP 가 아니다.** 로컬판의 정의적 성질이 "검색 경로 런타임 의존성 0" 이라
> 스킬 + `Grep`/`Read` 도구만 쓴다(`DECISIONS.md` D8). MCP 를 쓰는 것은 C 뿐이다.

## 재는 장치가 둘이다 — 축이 다르다

**나란히 놓고 비교하지 말 것.** `rank.py` 는 순위를, `agent.py` 는 실제 비용을 잰다.

### `rank.py` — 순위만, $0

정답이 **몇 위**에 오나. 로컬판은 스킬 절차(ALIASES → TREE → 본문)를 밟고 **어느
단계에서 찾았는지** 남긴다. 틀렸을 때 **무엇을 대신 골랐는지**가 랭킹 진단의 단서다.

```bash
python3 eval/rank.py
```

**비용은 안 잰다.** 예전에는 여기서 문자 수·지연도 쟀는데, 그것은 내가 가정한 접근
패턴이지 측정이 아니었다. `agent.py` 옆에 같은 표 모양으로 놓이니 **4자리 차이 나는
지연(8ms 대 73,000ms)을 비교로 읽게** 됐다. 흉내는 걷어내고 실측만 남겼다.

**A 원시 grep 은 대상이 아니다** — 랭커가 없어 순위라는 개념이 없다.

### `agent.py` — 진짜 세션

`claude -p` 로 **케이스마다 독립된 Claude Code 세션**을 띄운다. 실제 토큰 수(`usage`)와
비용(`total_cost_usd`)이 나온다.

```bash
eval/setup.sh up
python3 eval/agent.py --groups G01 G05 --reps 3 --budget 20
eval/setup.sh down
```

**중단돼도 이어받는다** — 끝난 조합은 건너뛴다(워밍과 실패는 안 센다). `--budget` 이
USD 상한이고 **워밍도 그 예산을 쓴다.** `--warmup` 은 케이스마다 버리는 1회를 먼저
돌려 **MCP 첫 호출 오버헤드**를 분리한다(파일럿에서 C 의 첫 질의만 603K, 이후
183K·259K 였다).

### 케이스 격리 — `setup.sh` 가 설치본을 내린다

`--plugin-dir` 는 플러그인을 **추가**할 뿐 사용자 레벨 설치본을 끄지 않는다. 설치본이
있으면 세 케이스가 서로의 것을 본다(전부 실측):

| | 보면 안 되는 것 | 안 막으면 |
|---|---|---|
| A | wikilens-local · wikilens-client | 로컬 스킬이 `config.json` 의 **진짜 볼트**를 가리켜 격리가 경로로 우회된다 |
| B | wikilens-client | **B 가 MCP 를 쓴다** — B 와 C 가 같은 것을 재게 된다(실제로 그랬다) |
| C | wikilens-local | MCP 대신 grep 을 쓸 수 있다 |

**도구 이름으로는 못 막는다** — `Skill(이름)` 형식이 안 먹고, `Skill` 통째로 막으면
B·C 가 자기 스킬을 못 쓴다. `setup.sh up` 이 설치본을 내리고 `--plugin-dir` 만
남긴다. 그러면 각 세션이 자기 플러그인만 본다:

```
A 원시grep   Bash 만
B 로컬판     Skill + Bash + Read
C 서버판     mcp__…__search · read · grep
```

**`down` 이 되돌린다 — 벤치가 죽으면 안 돌아오므로 끝나면 반드시 부를 것.**
도구 이름은 매 측정에 기록되므로, 격리가 깨지면 결과 파일에서 바로 보인다.

### 실험이 둘이다 — cold 와 warm

```bash
eval/setup.sh up cold    # 궤적 비움 (기본)
eval/setup.sh up warm    # 궤적 유지
```

**궤적을 비울지가 곧 무엇을 재느냐다.**

| | 재는 것 |
|---|---|
| **cold** | **검색 엔진 자체** — BM25+앵커 대 grep. 학습이 없어 셋이 같은 출발선 |
| **warm** | **학습이 값어치를 하나** — 회차가 갈수록 C 가 나아지는지 |

**둘 다 필요하다.** warm 만 재면 서버판이 이겨도 그것이 형태소 분석 덕인지 학습 덕인지
못 가린다. **cold 와의 차이가 곧 학습의 기여분**이다.

서버판의 존재 이유가 "세션을 넘어 쌓이는 학습" 이므로 cold 만 재면 **C 를 절반만 재는
것**이다. 반대로 warm 은 **비대칭**이다 — C 만 이전 회차를 물려받고 A·B 는 매번
처음부터다. 그것이 학습 층의 설계 그대로지만(A·B 에는 학습이 아예 없다) 리포트가
그 사실을 밝힌다.

**모드는 서버에 물어 기록한다** — 플래그로 받으면 cold 로 띄워놓고 warm 이라 적는 일이
생긴다. 매 측정에 그 시점의 궤적 수가 남고, `report.py` 가 그것으로 학습 곡선을 낸다.

### warm 에서 질의 순서가 곧 가설이다 — `--pattern`

```bash
python3 eval/agent.py --pattern repeat   --reps 5 --groups G04
python3 eval/agent.py --pattern transfer --reps 5 --groups G04
```

| | 순서 | 재는 것 |
|---|---|---|
| `spread`(기본) | q0,q1,q2 × N | 섞여서 원인 분리가 안 된다 |
| `repeat` | q0×N, q1×N, q2×N | **정확 반복** — c=1.0 이라 발동해야 한다 |
| `transfer` | q0 를 N−1회 학습 → q1,q2 시험 | **표현 전이** — c 가 낮아 안 될 것이다 |

권장 순서: **cold 한 벌 → warm + repeat → warm + transfer.**

## 돌리기 전에 계산해 둔 것 (2026-08-12)

에이전트 벤치는 세션당 $0.53 이라, **정적으로 먼저 예측하고 그것을 시험**했다.
아래는 전부 실측이고 `$0` 이 들었다.

**① 사전확률이 전부 상한에 붙는다.** BM25 점수가 13% 폭으로 압축돼 있어
`score/top` 정규화가 변별을 못 한다 — 10위 문서도 0.85 다. 그래서 어휘가 찾는
문서는 `ebLower(1,0,0.85)=0.62` 로 **1회 관측이면 문턱(0.45)을 넘는다.**

**② 표현 전이는 안 된다.** 서빙되려면 `0.62 × c >= 0.45`, 즉 커버리지 `c >= 0.73`
이 필요한데, 그룹 안 세 표현의 **항 겹침이 0~3개**(질의 항 4~8개)라 c 가 0.17~0.43 이다.

실측으로 확인했다 — q0 로 5회 학습시킨 뒤:

```
G02  q0 힌트 1건 ○   |  q1 힌트 0건  q2 힌트 0건
G04  q0 힌트 1건 ○   |  q1 힌트 0건  q2 힌트 0건
```

**정확 반복만 발동하고 다른 표현에는 안 닿는다.**

**③ 그리고 이것이 이 측정에서 나온 가장 중요한 것:**

> **학습 층이 가장 필요한 곳에서 가장 늦게 발동한다.**

`hints()` 는 어휘 결과에 없는 문서에 **기본 사전확률 0.3** 을 준다
(`TrajectoryStore.kt:337`, `priors[pid] ?: 0.3`). 그러면:

```
어휘가 이미 찾는 문서   prior 0.85 → 1회면 발동   ← 학습이 필요 없는 경우
어휘가 못 찾는 문서     prior 0.30 → 7회 필요     ← 학습이 존재하는 이유
```

**7배 차이다.** 실측: G01(어휘 미도달)을 반복하니 누적 7회째에 처음 힌트가 나왔고,
계산값과 일치한다. `S = 학습 힌트만` 이라는 이 레이어의 존재 이유가 정확히 가장
느린 경로다.

이것은 벤치의 결함이 아니라 **제품의 설계 관찰**이다 — 되돌리려면 기본값을 올리거나
어휘 미도달 문서를 다르게 다뤄야 하는데, 둘 다 오답을 늘릴 수 있어 측정이 먼저다.

**세션 분리가 이 벤치의 핵심이다.** 한 세션에서 세 방식을 다 하면 첫 방식에서 답을
알아버려 나머지가 무효가 된다. `claude -p` 는 매번 새 프로세스라 컨텍스트가 안 샌다.

**비싸다** — 파일럿 9세션이 $4.79 였다. 전체 90세션이면 약 $48 이다.

## 질의 — `queries.py`

10그룹 × 3질의. **같은 답을 내야 하는 유사 질의**를 묶었고, 코퍼스를 직접 읽어
사람이 치는 말로 썼다. 설계 근거와 함정은 그 파일의 독스트링에 있다.

**순위로 질의를 고르지 않았다** — 랭커에 맞춰 시험지를 고치면 순환 논리가 된다.

## 결과 해석에서 조심할 것

**변동이 크다.** 파일럿에서 같은 케이스가 96K~704K 토큰으로 **7배** 흔들렸다.
케이스 간 차이(11%)보다 훨씬 크다 — **단발 측정으로 토큰 우열을 주장하면 안 된다.**
반복하거나, 차이가 변동 폭을 넘을 때만 말할 것.

**쉬운 그룹은 변별하지 못한다.** G06 은 세 방식 다 3/3 으로 맞혔다. 돈만 쓰고
정보가 없으므로, 예산이 한정되면 앞선 정적 측정에서 갈렸던 그룹부터 돌릴 것.

**궤적이 쌓인다.** C 케이스는 MCP 프록시가 `sessionId` 를 보내므로 질의가 학습으로
기록된다. `setup.sh` 가 전용 서버를 띄우는 이유이고, **운영 서버로 돌리면 안 된다.**

## 형상 — 어느 코드에서 잰 값인가

측정마다 **커밋(또는 태그)과 더러운 트리 여부**를 남긴다. 결과만 남고 코드가 바뀌면
그 수치는 복원 불가가 된다 — 이 저장소가 `13,921건 2.44초` 로 한 번 겪은 일이다.

```
=== 형상 ===
  eval-baseline-2026-08-12                              90건
  (기록 없음)                                            9건
  ★ 형상이 섞여 있다 — 코드가 바뀐 전후를 한 표에 넣고 있다
```

**더러운 트리는 표시한다** — 커밋 해시만 남기면 "그 커밋에서 나온 값" 처럼 읽히는데
사실이 아니다. C 케이스는 **서버 이미지 ID** 도 남긴다: 소스를 고치고 다시 안 지으면
옛 이미지가 도는데(실제로 겪었다), 커밋만으로는 그것을 못 잡는다.

기준 태그는 `eval-baseline-2026-08-12` 다. **옮기지 말 것** — 코드가 바뀌면 새 태그를
단다. 옮기면 옛 결과가 어느 형상에서 나왔는지 복원할 수 없다.

```bash
python3 eval/report.py                    # 표

```

**손으로 옮겨 적은 표는 두지 않는다.** 그렇게 했더니 질의를 바꾼 순간 문서가 조용히
낡았다 — 질의 4개가 전부 교체됐는데 문서는 옛 값을 말하고 있었다. `results/*.jsonl`
이 정본이고 표는 거기서만 나온다.

리포트가 **IQR 이 겹치는 쌍을 스스로 지목한다.** 겹치면 우열을 말할 수 없다는 뜻이다.

`results/pilot-G06.jsonl` 은 에이전트 파일럿 9세션($4.79)이다 — 스키마를 통합하면서
옛 형식을 옮겨 놨다(`extra.migrated`).
